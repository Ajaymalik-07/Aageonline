# AageOnline — API Architecture & Security Contract

## 1. Core API Principles

1. **Protocol:** Strict JSON over HTTPS (TLS 1.3 preferred, minimum TLS 1.2).
2. **Zero Client Authority:** The client may request quotes or submit bids; the server exclusively calculates prices, authorizes requests, checks eligibility, verifies payments, and updates rankings.
3. **Idempotency:** All state-changing endpoints (`POST`, `PATCH`, `DELETE`) require a unique client-provided `Idempotency-Key` header (UUID v4).
4. **Correlation:** Every request is assigned a unique `X-Request-Id` which propagates through logging, payment gateways, and audit logs.
5. **No Floating-Point Money:** All monetary values are exchanged as exact 64-bit integers in minor units (paise: ₹1.00 = `100`).
6. **Object-Level Authorization:** Authenticated identity is verified against resource ownership on every private endpoint.

---

## 2. Global Headers & Conventions

### Request Headers
- `Authorization: Bearer <token>` (Required for authenticated endpoints)
- `Idempotency-Key: <uuid-v4>` (Mandatory for all mutating operations)
- `X-Request-Id: <uuid-v4>` (Optional client tracing ID; generated by server if omitted)
- `Content-Type: application/json`

### Response Headers
- `X-Request-Id: <uuid-v4>`
- `Content-Security-Policy` & `Strict-Transport-Security` (on all responses)
- `Cache-Control`: Enforces caching tiers (Public cached, Private `no-store`).

```http
GET /api/v1/markets
GET /api/v1/markets/:marketId
GET /api/v1/markets/:marketId/ranking
GET /api/v1/businesses/:businessId
```

### Public Data Masking Rules:
- Returns public business name, slug, category, location, verification status, and public visibility position.
- **NEVER EXPOSES:** Owner user IDs, private contact details, gateway payment references, internal transaction IDs, or risk scores.
- Cached at edge/CDN with strict revalidation tags (TTL 30s to 3600s).

## 5. Bidding & Position Purchase Endpoints

### 5.1 Request Position Quote
```http
POST /api/v1/markets/:marketId/position-quote
```
**Request Body:**
```json
{
  "targetPosition": 1
}
```
**Server Processing:**
- Re-reads current incumbent qualifying amount under a read lock.
- Computes minimum required amount: $\text{incumbent} + 100\text{ paise}$ (or base entry fee if vacant).
- Generates a cryptographically signed or server-stored quote valid for 120 seconds.

**Response:**
```json
{
  "data": {
    "marketId": "mkt_jaipur_interior",
    "targetPosition": 1,
    "currentQualifyingMinor": 2000000,
    "minimumRequiredMinor": 2000100,
    "quoteExpiresAt": "2026-10-07T10:15:00Z"
  }
}
```

### 5.2 Submit Position Purchase (Initiate Bid)
```http
POST /api/v1/markets/:marketId/bids
Idempotency-Key: 9b1deb4d-3b7d-4bad-9bdd-2b0d7b3dcb6d
```
**Request Body:**
```json
{
  "businessId": "biz_abc_123",
  "targetPosition": 1,
  "offeredAmountMinor": 2000100
}
```
**Server Security Checks:**
1. Verify user owns `businessId` (Object Authorization).
2. Verify `business.status === 'ACTIVE'`.
3. Recalculate target position minimum qualifying amount.
4. **Assert:** `offeredAmountMinor >= recalculatedMinimum`. (Client's price is rejected if superseded).
5. Create transaction record with status `PAYMENT_PENDING`.
6. Return payment initiation intent.

**Error Scenarios:**
- `409 Conflict`: `TARGET_POSITION_SUPERSEDED` (Another transaction moved the qualifying floor).
- `422 Unprocessable`: `INVALID_BID_QUALIFICATION` (Offered amount fails strictly-greater rule).
- `403 Forbidden`: `UNAUTHORIZED_BUSINESS_ACCESS` (Caller does not own business).

## 6. Payment Endpoints

### 6.1 Create Payment Intent
```http
POST /api/v1/payments/create
Idempotency-Key: <uuid>
```
**Server Processing:**
- Verifies bid record is in `PAYMENT_PENDING` state.
- Initializes gateway order (e.g. Razorpay) with amount derived strictly from the server-stored transaction record.
- Ignores any client-supplied amount parameter.

### 6.2 Authoritative Payment Status Check
```http
GET /api/v1/payments/:paymentId
```
- Polled by frontend while payment confirmation is in-flight.
- Returns authoritative transaction status (`PAYMENT_CONFIRMED`, `RANKING_PENDING`, `RANKING_CONFIRMED`, or `PAYMENT_FAILED`).

### 6.3 Gateway Webhook Route
```http
POST /api/v1/payments/webhook
X-Provider-Signature: <hmac-signature>
```
**Processing Protocol:**
1. **Raw Body Verification:** Verify HMAC signature against unparsed payload bytes using provider webhook secret.
2. **Replay Check:** Discard payloads with timestamps older than 300 seconds.
3. **Event Idempotency:** Check `provider_event_id` in `webhook_events` table. If already processed, return `200 OK` immediately.
4. **Transaction Cross-Check:** Look up internal transaction by `order_id`:
   - Assert `webhook.amount == transaction.amount_minor`.
   - Assert `webhook.currency === 'INR'`.
   - Assert `transaction.status === 'PAYMENT_PENDING'`.
5. **Atomic Execution:** Begin database transaction to mutate status to `PAYMENT_CONFIRMED` and trigger the Ranking Engine mutation.
6. **Fail-Closed:** If amount or currency mismatch detected, mark transaction `RECONCILIATION_REQUIRED` and raise P1 alert.

## 9. Standardized Error Response Contract

```json
{
  "error": {
    "code": "TARGET_POSITION_SUPERSEDED",
    "message": "Another business has placed a higher qualifying bid for position #1.",
    "requestId": "req_84f9a0c1",
    "details": {
      "marketId": "mkt_jaipur_interior",
      "targetPosition": 1,
      "updatedMinimumRequiredMinor": 2500100
    }
  }
}
```

### Critical Security Error Codes:
| Code | HTTP Status | Description |
| :--- | :--- | :--- |
| `TARGET_POSITION_SUPERSEDED` | 409 | Race condition: Target position floor has increased |
| `INVALID_BID_QUALIFICATION` | 422 | Bid does not strictly exceed incumbent qualifying amount |
| `UNAUTHORIZED_BUSINESS_ACCESS` | 403 | Caller does not own or manage the target business |
| `UNVERIFIED_WEBHOOK_SIGNATURE`| 401 | Webhook HMAC cryptographic signature verification failed |
| `IDEMPOTENCY_CONFLICT` | 409 | Reused idempotency key with conflicting request payload |
| `PAYMENT_AMOUNT_MISMATCH` | 400 | Gateway webhook amount differs from internal transaction |
| `TRANSACTION_EXPIRED` | 410 | Payment hold window has elapsed |
| `RATE_LIMIT_EXCEEDED` | 429 | Request rate exceeded allowable threshold |
